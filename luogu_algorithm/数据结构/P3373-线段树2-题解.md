# P3373 线段树 2 题解（双 lazy：乘 + 加）

> 2026-08-25 完成 | 线段树第四档（双懒标记）| 用户从零手写 + 本地样例 17/2 过 + 暴力对拍 2000 组通过
> 一句话定位：**给数组做区间乘、区间加、区间求和（mod p）。一个 lazy 变两个，难在「乘法会污染加法」。**

---

## 〇、题面

- `n` 个数，`m` 次操作，答案对 `p` 取模。
- 操作 1：`1 x y k` → 区间 `[x,y]` 每个数 **×k**。
- 操作 2：`2 x y k` → 区间 `[x,y]` 每个数 **+k**。
- 操作 3：`3 x y` → 查询区间 `[x,y]` 的和 `mod p`。
- 数据范围：`n,m ≤ 1e5`，`p` **不保证是素数** → 不能用逆元，必须存真实值。
- **输入第一行是 `n m p` 三个数**（不是 `n p`！样例踩过的坑）。

---

## 一、难在哪：一个 lazy 变两个，还打架

P3372 只有「加」，一个 `lazy_add` 就够。这题有乘有加 → 要 `lazy_mul` + `lazy_add`。

但它们**不能独立记账**。想想一个致命场景：

> 区间先被 **+3**，后被 **×5**。孩子每个数真实值 = `(原值+3) × 5`。
> 如果只记 `lazy_add=3`、`lazy_mul=5`，原值早忘了——add 该记 3，实际是 `3×5=15` 的账。

这就是双 lazy 的经典坑：**乘法会污染加法标记**。两个标记分开记，回溯永远对不上账。

---

## 二、核心洞见：把「累计操作」统一成一个公式

不管标记怎么存，统一**一个节点代表的累计操作**：

```
每个数 x → x × mul + add        （先乘后加）
```

所有对这个区间的操作（多少步都行），最终都等价成这一句话。于是两种 update 变得干净：

| 操作 | 对每个数 | 标记怎么改 |
|---|---|---|
| **×k** | `(x×mul+add)×k = x×mul×k + add×k` | `mul *= k`，**`add *= k`** ← 污染 |
| **+k** | `x×mul + add + k` | `add += k` |

**为什么乘法会污染加法？** 因为整个表达式 `x×mul+add` 要整体乘 k，`add` 那项必须跟着乘。这一行 `add *= k` 写漏 = 全错。

---

## 三、pushDown 的合并（最容易写反的一行）

父挂 `(mul, add)` 下推给孩子，孩子自己有 `(mul_c, add_c)` = `x → x×mul_c + add_c`。父的操作再套一层：

```
x → x×mul_c + add_c              （孩子自己的账）
  → (x×mul_c + add_c)×mul + add   （父的账再套上来）
  = x×mul_c×mul + add_c×mul + add
```

所以孩子标记合并：

```
child.mul = child.mul × mul
child.add = child.add × mul + add     ← 先乘父的 mul，再加父的 add，顺序反了也错
```

### 本课的一个实现变体：拆成「先乘后加」两步

把合并写成顺序两步，数学上等价（因为乘对加有分配律）：

```
mul 块：child.data *= mul;  child.mul *= mul;  child.add *= mul;   node.mul = 1
add 块：child.data += add×len;  child.add += add;                  node.add = 0
```

效果恰好等于上面的合并公式——**mul 块先把 child 的 add 乘了，add 块再加**。这是「先乘后加」的物理含义。⚠️ 顺序敏感：mul 块必须在 add 块之前，且每步都要取模。

---

## 四、update：整块覆盖分两档

```
update_mul(node,l,r,ql,qr,k):
  无关 → return
  整块 → data = data×k %p;  mul = mul×k %p;  add = add×k %p;  return   // 污染行!
  劈两半 → pushDown → 左 → 右 → 回溯 data = (左+右) %p

update_add(node,l,r,ql,qr,k):
  无关 → return
  整块 → data = (data + k×(r-l+1)) %p;  add = (add+k) %p;  return
  劈两半 → pushDown → 左 → 右 → 回溯 data = (左+右) %p
```

和 P3372 的区别就两点：**update 拆成乘/加两个函数**、**乘法整块那档多一行 `add *= k`**。其余三件套、pushDown 时机、回溯完全一样。

---

## 五、取模纪律（P3373 最大的隐形坑）

`%p` 是这题的题眼。**规则：任何一行写着 `+=` 或 `= 左+右` 或 `×=` 的地方，都要 `%p`。**

漏在哪会错？举反例：`k` 和 `a[i]` 都能到 `1e9`，pushDown add 块 `add × len` 会到 `2e9 × 1e5 = 2e14`，必然不是模 p 的结果 → query 整块覆盖直接返回它 → **错答案**。所以：

- build 叶子 `a[l]%p`、内部回溯 `(左+右)%p`
- pushDown mul 块 6 行全 `%p`
- pushDown add 块 4 行全 `%p`（最容易漏！）
- update 两档整块覆盖 + 回溯全 `%p`
- query 返回 `(left+right)%p`

**一个特殊点：** pushDown 拆两步时，mul 块先执行 `%p`，add 块再用结果——顺序不能换。

## 六、复杂度

| | 时间 | 空间 |
|---|---|---|
| 每次操作 | **O(log N)** | O(4N) |

`n=1e5` → 1e5 × log ≈ 1.7e6，秒过。

## 七、本课踩的坑（全记录）

1. **样例输入格式看错**：第一行是 `n m p` 三个数，写两个数会把 `p` 读成 0 → 全 `%p` 变 `%0` 崩。
2. **`mul` 标记初值**：乘法单位元是 **1**，不是 0！`build` 时 `mul=1, add=0`。
3. **乘法污染加法忘写**：update_mul 整块档漏 `add *= k` → 顺序信息丢失，先乘后加/先加后乘分不出来。
4. **pushDown add 块漏 `%p`**：编译器抓不到，样例碰巧过，对拍 2000 组才可能揪出来。
5. **回溯行 `(左+右)` 忘 `%p`**：和上一条同族。
6. **笔误大会**：`ndoe`/`node`、`.date`/`.data`、`letf`/`left`、struct 缺 `;`——全是对拍前编译器抓的，不丢人，但养成「写完整段再编译」的习惯能少跑两轮。

## 八、双 lazy 手写模板（背下来）

```cpp
struct Node{ ll data, add=0, mul=1; };       // mul 初值 1!

void build(node,l,r)                          // 叶子 data=a[l]%p; 内部 (左+右)%p
void pushDown(node,l,r)                       // 先乘后加:孩子 data/mul/add 乘 mul,
                                              //         再 data+=add×len, add+=add; 全 %p
void update_mul(node,l,r,ql,qr,k)
  // 无关→return; 整块→data×=k,mul×=k,add×=k(污染!),return; 劈→pushDown→左→右→回溯
void update_add(node,l,r,ql,qr,k)
  // 无关→return; 整块→data+=k×len,add+=k,return; 劈→pushDown→左→右→回溯
ll query(node,l,r,ql,qr)
  // 无关→0; 整块→data; 劈→pushDown→左+右, %p
```

**记忆钩子：**
- 一个操作统一成 `x×mul + add`（先乘后加）。
- **乘法污染加法**：`×k` 时 `add` 也要 `×k`，这是双 lazy 唯一的灵魂。
- pushDown 孩子合并：`child.add = child.add×mul + add`（先乘父 mul 再加父 add）。
- 全程 `%p`，尤其 `+=` 和 `左+右` 的回溯行。
- `n m p` 三个数读第一行。
