## 〇、动手层回顾：TCP 字节流 & send/recv 语义

### 1. 应用层 vs 内核层（关键桥梁）
- **应用层**：你自己的 `recv()`/`send()` 循环、自己的缓冲区。
- **内核层**：TCP 的接收缓冲、发送缓冲、滑动窗口、Nagle、延迟 ACK。
- 很多"怎么不按我想的走"的困惑，根源都是分不清数据是卡在**应用层缓冲区**还是**内核缓冲区**。

### 2. TCP 字节流，没有消息边界
- **部分发送**：`send()` 只把内核发送缓冲能收下的部分拷走，剩下的**留在你的应用缓冲区**（不丢，只是没发出去）。是"截断"，不是"损坏"。
- **部分接收**：`recv()` 只要内核接收缓冲有**任何**数据就返回（永远不等满）。剩下的继续留在内核缓冲，等下次 recv。
- 粘包/拆包 = 同一现象的两面：发送侧看是"多个消息粘在一起发"，接收侧看是"一条消息被拆开收"。
- 可靠性对比：TCP 部分收/发不丢，UDP 是真的丢包。

### 3. send/recv 语义细节
- `recv()` 返回条件：**只要有数据就返回**，不凑够 len；只有缓冲空才阻塞。
- 第 4 个参数是 **flags**，**不是超时**！超时用 `setsockopt(SO_RCVTIMEO/SO_SNDTIMEO)`。
- `recv()` 返回 0 = 对方 FIN 了（EOF）；返回 -1 = 出错。
- **send() 到已关闭的 socket → SIGPIPE 杀进程**（这就是 client.cpp 坑④）。

### 4. 消息结束的三种约定
| 方案 | 例子 |
|------|------|
| 固定长度 | stress_client 的 2048 |
| 长度前缀 | HTTP 的 Content-Length |
| 分隔符 | chat 的 '\n'（回车） |

### 5. client.cpp 复习踩的 4 个坑
1. **坑①** `while(total<strlen(buff))`：recv 覆盖 buff 后 strlen 变垃圾 → 先把 `msg_len=strlen(buff)` 存起来，循环用 `msg_len-total`。
2. **坑②** `strlen(buf)` 变量名打错（buff 是两个 f）→ 编译错。
3. **坑③** 回声 cout 放循环里 + 结尾 `\0` 注释掉 → 循环外 `buff[total]='\0'` 后打印一次。
4. **坑④** `if(n<=0)break;` 只跳出内层循环 → 外层继续对已关闭 socket send = SIGPIPE → 加 `flag` 标记，内层结束后判断再 break。
5. 另有：`buff[1024]` 存满再 `buff[n]='\0'`（n==1024）→ **越界写**。

## 一、三次握手

1. **SYN** → 客户端 SYN=1, seq=x（"我想连"）
2. **SYN+ACK** → 服务器 SYN=1, ACK=1, seq=y, ack=x+1（"可以，我也想连"）
3. **ACK** → 客户端 ACK=1, seq=x+1, ack=y+1（"好，连上了"）

**为什么不能两次握手？**
- 服务器要确认"自己发出的 SYN 到达客户端"。若只有 1、2 步，客户端可能收不到第 2 步（旧 SYN 重传），服务器以为连上了、客户端不知道 → 服务器白白挂起半开连接（SYN_RECVD），浪费资源。
- 三次握手保证**双方都能确认对方收到了自己的 SYN**。

**为什么 SYN 不能携带数据？**
- 服务器还没准备好接收数据（连接未建立），收到带数据的 SYN 不知道往哪交。

## 二、四次挥手 + TIME_WAIT

### 四次挥手流程（设 A 主动关）
1. A → FIN（"我不发了"，A 进 FIN_WAIT_1）
2. B → ACK（"收到你的 FIN"，B 进 CLOSE_WAIT，A 进 FIN_WAIT_2）
3. B → FIN（B 发完了，B 进 LAST_ACK）
4. A → ACK（A 进 TIME_WAIT）

### 为什么 4 次不是 3 次？
- B 的 **ACK 和 FIN 不能合并**：B 收到 FIN 时**可能还有数据要发**，必须先 ACK 表示"收到你的 FIN"，等数据发完再发自己的 FIN。
- 三次握手 SYN 和 ACK 能合并，是因为连接刚建立、服务器没有数据要发。

### TIME_WAIT（主动关闭方停留 2MSL）
两个作用：
1. **最后一个 ACK 可能丢失** → 对方会重传 FIN，你还在等，能补发 ACK。（若直接关，对方重传的 FIN 没人理，对方永远进不了关闭态）
2. **让旧报文在网络里自然消亡**（2MSL）→ 之后端口复用是干净的，不会收到上一个连接的残留包。

**谁是主动关闭方？** 谁**先调用 close()**，谁进 TIME_WAIT（跟客户端/服务器角色无关）。

### 现实坑：TIME_WAIT 累积
- 短连接服务大量断开后，TIME_WAIT 的端口堆积。
- 服务端重启时报 `bind error: Address already in use` → 用 `SO_REUSEADDR`。
- 高频短连接服务要考虑 TIME_WAIT 资源回收策略。

## 三、流量控制（滑动窗口）

### 核心
- 接收方在报文里带 **win（窗口）** = 自己空闲缓冲区大小。
- 发送方未确认的字节数 ≤ 窗口 → 不会把对方缓冲区撑爆。
- **零窗口**：接收方缓冲满了，win=0，发送方暂停。

### 零窗口死锁 + 解决
- 死锁成因：接收方有了空间，发**纯窗口更新报文**（不带数据）；但**纯 ACK/窗口更新不被重传**，若丢失：
  - 发送方：一直在等新窗口信息；
  - 接收方：一直在等确认（等确认纯 ACK 到达）；
  - **双方都等对方，死锁**。
- 解决：**持续计时器（persist timer）**——发送方定时发 **1 字节窗口探测报文**，逼对方回窗口状态。

## 四、拥塞控制

> 区别于流量控制：流量控制是**点对点**（接收方缓冲够不够）；拥塞控制是**全网**（路由/中间链路堵不堵），没有显式通知，**靠丢包推断**。

### 慢启动（指数）
- cwnd 从 1 开始，每个 RTT 翻倍：1→2→4→8…
- **为什么翻倍**：一开始不知道网络上限，翻倍快速逼近；到 ssthresh（慢开始门限）切换。
- ssthresh **是动态的**：初始很大，丢包时减半。

### 拥塞避免（线性）
- 到 ssthresh 后，cwnd 每个 RTT **+1**（线性），避免又拥塞。

### 快重传 + 快恢复
- 收到 **3 个重复 ACK** → 立即重传丢失的段（不等超时），ssthresh **减半**，从 ssthresh 线性增长（**快恢复**，不是回到慢启动）。
- **为什么 3 个重复 ACK 是"轻度"信号**：后续数据还在到达，说明只是丢了某个包，网络没崩 → 不必从头慢启动。

### 两种"坏"的级别
| 信号 | 严重度 | 反应 |
|------|--------|------|
| 超时（严重） | 网络可能真堵/断开 | cwnd=1，从头慢启动 |
| 3 个重复 ACK（轻度） | 只是丢了个包 | 快恢复，cwnd 减半 |

### 拥塞崩溃（概念）
网络过载 → 大量重传 → 占用更多带宽 → 更堵 → 有效吞吐趋近 0。

## 五、粘包 / 拆包

### 本质
TCP 是字节流，**没有消息边界**。发送端多次 send 的数据可能一次到达（粘包）；一次 send 的大数据可能多次 recv 到（拆包）。

### 三种解决约定（面试要背全）
1. **固定长度**：不够补 0 或填充（实现简单，浪费空间）。
2. **长度前缀**：先发 4 字节长度，再发数据（HTTP Content-Length 同款，灵活常用）。
3. **分隔符**：约定特殊字符结尾（聊天 '\n'；缺点：数据里不能出现该字符，需转义）。

## 六、Nagle 算法 + TCP_NODELAY

### 规则
**只要有一个小报文段还没被 ACK，新产生的的小数据就攒着不发**，等：ACK 回来，或数据攒满一个 MSS 再发。

### 本质
**用延迟换带宽**——把小数据攒成大段，省头部开销（每段固定 IP20+TCP20=40 字节头）。

### 经典坑：Nagle + 延迟 ACK ≈ 40ms
- 接收方延迟 ACK：故意拖 ~40ms 再 ACK，想把 ACK 搭在返回数据上。
- 两者叠加：
  ```
  发小包A → 在途等ACK → 发小包B（被Nagle攒着）
  对端拖40ms才ACK → 你干等 → ACK回来B才能发
  ```
- 交互式应用（telnet 每敲一个键就发一个小包）场景下，**每个操作白白多 40ms**。

### TCP_NODELAY
- **关闭 Nagle**：小包立即发，不等 ACK。
- 延迟敏感应用要开：在线游戏、远程桌面、SSH 交互、聊天。

### 关掉 Nagle 的代价（面试精确版）
1. **头部开销**：小包也要独享 40 字节头（IP20+TCP20）。
2. **算账**：每秒 5000 个控制包 → `5000×40B = 200KB/s` 纯头部，数据可能只有 10KB，**95% 带宽在运头**。
3. **连锁反应**：大量小包占满路由转发队列 → 排队抖动 → 反而更卡（这正是 Nagle 想避免的）。

### 经验法则
| 场景 | Nagle | 理由 |
|------|-------|------|
| 在线游戏/远程桌面/SSH | **关**（TCP_NODELAY） | 延迟优先，宁可浪费带宽 |
| 文件下载/大响应/批量 | **开**（默认） | 吞吐优先，报文本来就大，浪费可忽略 |

## 七、close vs shutdown

### close(fd)：释放 fd
- **双向关闭**：发 FIN（不再发）同时不再收。无法只关一半。
- **引用计数**：socket 可能被多个 fd 指向（fork 共享）。close 只是 **-1**，**归零才真正断开**。
- 面试连环问：两个进程共享 socket，A close 了 B 还用，连接断吗？→ **不断**，计数只减到 1。

### shutdown(fd, how)：关一半
| how | 效果 |
|-----|------|
| `SHUT_WR` | **立刻发 FIN**："我不发了，但还愿意收你的数据"（半关闭） |
| `SHUT_RD` | "收也不收了"，之后到的数据直接丢弃 |
| `SHUT_RDWR` | 双向都关 |

### 三条核心区别
1. **方向**：close 只能双向全关；shutdown 可只关发送、保留接收。
2. **fd**：close 释放 fd；shutdown **不释放** fd，之后还得 close。
3. **引用计数**：close 等到归零才断；shutdown **立刻生效**（哪怕还有别的 fd 指着，FIN 当场发出）。

### 现实场景（HTTP）
- 客户端发完请求体 → `shutdown(SHUT_WR)` 发 FIN。
- 服务器 `recv` 读到 0（EOF）→ 知道请求完整到达 → 顺着同一连接回响应。
- 服务器还能回数据，因为客户端只是关了发送、没关接收。

## 九、connect 失败模式（8/22 补）

### ① ECONNREFUSED（连接被拒绝）—— 立即失败
- 机制：SYN 发到目标主机，主机**在线**但目标**端口没人监听** → 内核回 **RST** → 立即返回 -1，errno = ECONNREFUSED。
- 一句话：**"我不服务这个端口，明说了。"** 对方回应了，只是拒绝。
- 排障：**refused → 查服务起没起。**

### ② ETIMEDOUT（连接超时）—— 卡很久才失败
- 机制：SYN 石沉大海（路由不可达/包丢/防火墙静默丢弃/主机宕机）→ 无回应 → 超时计时器**重发多次**（总时长可达几十秒~2分钟）→ errno = ETIMEDOUT。
- 一句话：**"对面根本不理我。"** 不是拒绝，是没回音。
- 排障：**timedout → 查防火墙/路由。**

### 加餐
- `EHOSTUNREACH` / `ENETUNREACH`：目标**主机/网络不可达**（路由层直接报），失败速度介于两者之间。
- 排障口诀：**refused → 服务没起；timedout → 防火墙/路由；unreach → IP 不对。**

## 十、select / poll / epoll（8/22 补）

> 背景：服务器要同时管几千个连接，怎么知道哪个 fd 有数据？不能对每个 fd 阻塞 recv（第一个没数据的就卡死）→ 用 **I/O 多路复用**：一个函数让内核盯着 N 个 fd，告诉哪几个就绪。

### select（第一代）
- fd 集合（fd_set 位图）交内核逐个检查，返回后应用层再遍历找就绪的。
- 三个致命缺点：
  1. **数量上限 1024**（位图）。
  2. **每次全量拷贝**：每次调用都把全集从用户态拷进内核态，改完再拷回。
  3. **O(n) 双遍历**：内核扫全部 + 应用层再扫一遍全集。

### poll（第二代）
- 换链表（pollfd 数组），**突破 1024 上限**。
- 但**每次全量拷贝 + O(n) 扫描**一个没改。
- 一句话：select 的缺点 poll 只修了"上限"。

### epoll（第三代）
- 三个函数：**epoll_create**（创建内核事件表）/ **epoll_ctl**（增删改，ADD/DEL）/ **epoll_wait**（等事件）。
- 三个优点（对治 select 三缺点）：
  1. **不用每次拷贝**：fd 注册一次存在内核。
  2. **只返回有事件的 fd**：直接给就绪链表，遍历 O(就绪数) 而非 O(全部)。
  3. **无数量上限**，增删走**红黑树** O(log n)。
- 内核结构：**红黑树**（注册的 fd）+ **就绪链表**（有事件的 fd）。

### LT vs ET
- **LT 水平触发**（默认）：缓冲**还有数据**就每次通知，读不完下次还来 → 安全但唤醒多。
- **ET 边沿触发**：只在"没数据→有数据"**瞬间**通知一次，之后不再通知 → 高效但必须**循环读到 EAGAIN 榨干缓冲**，否则残留数据**永远无人读，连接假死**（再发新数据也不会触发，因为状态一直是"可读"，没有新边沿）。
- 配套铁律：**ET 必须配非阻塞 fd**，否则最后一次 recv 卡死在阻塞调用上。

### 对比表
| | select | poll | epoll |
|---|---|---|---|
| fd 上限 | 1024（位图） | 无（链表） | 无（红黑树） |
| 每次全量拷贝 | 是 | 是 | 否，注册一次 |
| 找就绪 fd 代价 | O(n) | O(n) | O(就绪数) |
| 触发模式 | 只水平 | 只水平 | 水平 + 边沿(ET) |

**一句话记忆**：select/poll = "把全班点名一遍"（select 还限 60 人）；epoll = "老师直接念出没交作业的那几个"。

## 八、基础总览：进程 / 线程 / fd / socket / IP / 端口 / 子网（8/22 补）

### 三层模型：进程的 fd 表 → 内核对象
- 进程有一张 **fd 表**（一个数组，下标就是 fd 编号），每一项指向内核里的一个对象（如 socket）。
- **fd = 门牌号/通讯录编号，socket = 房子/线路**。fd 表是**进程级**的。
- 线程共享所在进程的 fd 表 → **fd 属于进程，不属于线程**，线程拿编号就能操作对应的 socket。

### 进程 vs 线程
- **进程** = 资源分配单位（独立地址空间、fd 表）；**线程** = 进程内的执行流，共享进程资源（CPU 调度单位）。
- 多线程服务器：accept 一次 → 新 socket + 新 fd → 派一个线程（handle_client, client_fd）。

### socket vs fd
- **socket** = 内核里的连接对象（"线路"，内核维护，不属进程私有）。
- **fd** = 进程对这条线路的本地编号（内部通讯录条目）。
- 服务器 = **1 个监听 fd + N 个连接 fd**；客户端 = 每次连接 1 个 fd。
- fork 时子进程复制父进程 fd 表 → 两个 fd 指向**同一 socket** → 引用计数 = 2。close 只 -1，归零才真正断开。

### IP / 端口 / fd 三者区别
| | 是什么 | 类比 | 归属 |
|---|---|---|---|
| IP 地址 | 一台电脑的地址（192.168.1.100） | 街道门牌 | 全局，网络可见 |
| 端口 | 一台电脑里某个服务（8888） | 公司对外总机号 | 全局，拨号用 |
| fd | 进程内 socket 的本地编号 | 内部通讯录编号 | 本进程私有 |

- **IP + 端口 = 完整端点地址**（192.168.1.100:8888）。
- 一条 TCP 连接由**四元组**唯一确定：源IP + 源端口 + 目的IP + 目的端口。
- 127.0.0.1 = 回环地址（loopback），指本机自己。

### 子网（subnet）
- 每台电脑/服务器在网络上的地址叫 **IP 地址**（IPv4 = 4 段 0-255，如 192.168.1.5）。
- 家用路由器的私有地址段：**192.168.x.x**（最常见）、10.x.x.x、172.16~31.x.x。
- **子网掩码** 255.255.255.0（写作 /24）：把 IP 拆成**网络号 + 主机号**。192.168.1.5/24 = 网络 192.168.1 + 主机 5。
- **子网** = 一个局域网；同子网内直连，跨子网走**路由器**。

## 十一、多线程复习（8/22 补）

### 数据竞争 / atomic
- `x++` = load / inc / store 三步；两线程各 10 万次 → 结果 ∈ [100000, 200000]（丢更新）。
- `atomic<int>` → x++ 成为单条原子 RMW 指令（lock xadd）→ 严格 200000。原子是"单个操作"原子，不是"一串操作"原子。

### 锁粒度（granularity）
- 细粒度（每次 x++ 加锁）保留并行；粗粒度（锁整个循环）= 串行化 = 白开多线程。

### 死锁 Coffman 四条件
- 互斥 / 占有并等待 / 不可剥夺 / 循环等待。
- 工程上最常破「循环等待」：统一加锁顺序。
- `try_lock()`：非阻塞，立即尝试返回 bool（不等）；失败则释放已有锁再重试 → 破「占有并等待」。`try_lock_for()` 是 `timed_mutex` 的带超时版。

### 条件变量（治"干等"，mutex 治"同时抢"）
- 没有条件变量，消费者只能**忙等/轮询**（空转烧 CPU）。
- `cv.wait(lk, 谓词)` 原子做三件事：①释放锁 ②谓词为 false 就睡 ③唤醒后重拿锁、再查谓词，为真才继续。
- **必须用 `unique_lock`**：wait 要能放锁/收锁，`lock_guard` 没有 unlock()，传了编译都过不了。
- **谓词不能省**：被唤醒 ≠ 条件成立。①虚假唤醒（spurious wakeup，标准允许）②多消费者抢货——别人可能先取走。`wait(lk, pred)` 内部 = `while(!pred) wait(lk);`。
- 三种写法：`wait(lk)`=睡了再说（等唤醒）；`wait(lk, false谓词)`=睡到条件为真（安全）；`wait(lk, true谓词)`=连睡都不睡直接冲（自爆）。

### 单例三式
| 式 | 创建时机 | 线程安全 | 缺点 |
|----|---------|---------|------|
| 饿汉 | 程序启动（main 前，静态初始化） | 天生安全（创建发生在单线程阶段） | 不用也建，浪费 |
| 懒汉+DCL | 首次调用才 new | 有陷阱 | 快速路径无锁读 inst 与锁内写构成**数据竞争（理论 UB）**，可能拿到半成品对象 |
| Meyers | 首次调用才建（函数局部 static） | C++11 magic statics 保证只初始化一次 | 无，推荐 |

- DCL 代码：快速路径 `if(inst==nullptr)` 无锁 → 加锁 → 再查一次 → new。平时走快速路径不碰锁。
- 重排陷阱：`inst = new Config()` = 分配+构造+写指针三步，可能重排成"先写指针再构造"→ 别的线程看到非空但对象没造好。

### static 三种用法（8/22 补）
> static 两个灵魂：①共享一份（不属于某个对象，属于类/程序）②活到程序结束（生命周期贯穿全程）。
- **函数内 static 局部变量**：作用域=函数内（外面碰不到），生命周期=整个程序，只初始化一次（首次执行到才建）→ Meyers 单例（懒，用 C++11 magic statics 线程安全）。
- **static 成员变量**：全类共享一份，需类外定义，程序启动（main 前）初始化 → 饿汉单例（天生线程安全：创建发生在单线程阶段，之后全读）。
- **static 成员函数**：不用建对象就能调（`类名::函数`），没有 this 指针 → 只能访问静态成员 → getInstance 必须是它（构造私有，外面没有对象可调）。

## 十二、Reactor 模型（8/22 补）

### 核心思想
- **事件驱动 + 集中监听**：一个（少量）循环盯 N 个连接，谁就绪处理谁；平时连接在内核"待命"，不占线程。
- 对比「每连接一线程」（server_thread.cpp）：1 万连接 = 1 万线程 → 内存爆、切换开销炸；Reactor = 一个线程扛几万连接。

### 工作流程 4 步
1. **注册（register）**：把 fd + 关注事件登记进 epoll（epoll_ctl ADD）。
2. **监听等待（select/wait）**：epoll_wait 阻塞，线程睡在这里——这就是"一个线程扛 N 连接"的原因。
3. **分发（dispatch）**：决定事件交给谁（找到该 fd 的 handler）。
4. **处理（handle）**：handler 执行业务（read/write/算）。
- 区分：**分发 = "交给谁"；处理 = "干业务"**。

### 三种模型（演进 = 每步治上一步的瓶颈）
| 模型 | 结构 | 优点 | 代价/瓶颈 |
|------|------|------|----------|
| ① 单Reactor单线程 | 一个线程：accept+监听+分发+业务 | 简单、无并发问题（redis 早期） | 业务一重 handler 卡死全停；单线程只用一颗核 |
| ② 单Reactor多线程 | Reactor（accept+监听+分发）+ 线程池（业务） | 业务并行、多核用上 | accept+分发仍单线程，百万连接忙不过来；引入锁/数据竞争/复杂度 |
| ③ 主从Reactor多线程 | mainReactor（只 accept）→ 多个 subReactor（各管一批连接的读写监听）→ 线程池（业务） | accept 与监听拆分，百万连接首选（Nginx/Netty） | 复杂度最高 |

### Reactor 铁律
- 单循环里不能做耗时操作，否则一个 handler 卡死拖累全部连接 → 重活丢线程池（半同步/半异步）。

### 对照自己的代码
- epoll.cpp = **模型① 单Reactor单线程**：一个循环里既 accept 又 recv 又 send（if 监听fd → accept；else → recv）。
